# 대본

장표보다 대본을 먼저 만들고, **TTS 로 통으로 들어 보며 구성을 굳힌 뒤** 장면으로 넘어간다.
대본이 장표의 원본이다. 장면은 대본 구절에 매달리므로, 대본이 흔들리는 동안 장면을 많이 만들면 다시 만든다.

## 1. 청중이 가져갈 것 하나

- 먼저 정한다: 청중은 누구인가, 우리 일의 배경을 아는가, 끝나고 무엇을 해 보길 바라는가
- 예: 다른 팀 청중은 우리 프로젝트의 배경보다 일하는 방법에 관심이 많다 → **"무엇을 바꿨는지는 짧게, 어떻게 했는지는 길게"**. 무엇은 두 파트, 어떻게는 네 파트
- 마지막 파트는 효율이 아니라 **끝나도 남는 것**과 청중이 가져갈 행동으로 닫는다

## 2. 구성

- 파트 6~8개, 파트마다 문단 3~8개. 문단 하나 = 발표자 화면 한 칸 = 장표만 보기에서 문단 시작 한 번 누름
- 문단은 발표자 화면 34px 넉 줄 안(대략 120자 이하). `shoot.mjs --presenter` 가 넘치는 문단을 알려 준다
- data.js 파트마다 `context` 한 줄(이 파트가 하는 일). 장면을 만드는 사람이 의도를 읽는다
- 파트마다 쓴 이야기 장치를 **발표 전략**으로 남긴다(아래 표에서 2~5개). 피드백이 문장만이 아니라 의도에도 달린다

## 3. 이야기 장치 ("왜?"로 끌고 가는 이야기)

| 장치 | 예 |
| --- | --- |
| 아는 사건으로 시작 | 청중이 이미 본 지난달 앱 개편 |
| 통념을 대신 말하고 뒤집기 | "아이콘 하나 바꾸면 끝 아닌가?" → 목록에 없던 다섯 곳 |
| 숫자 하나로 미스터리 | 제목부터 숫자 하나("151번") |
| 성공 뒤 반전 | "완벽했다 → 그런데 너무 두꺼웠다" |
| 문제 재정의 | "숫자가 틀린 게 아니라 기본값이 틀렸다" |
| 실패담을 클라이맥스로 | "AI 가 틀린 날들". 청중은 AI 자랑을 기대하고 온다 |
| 3단 + 마지막 반전 | 둘은 "틀렸다", 셋째는 "0 이 가장 위험했다" |
| 의인화 · 하루 따라가기 | 에이전트의 아침 아홉 시부터 |
| 라벨 구조 | 문제 하나, 문제 둘. 귀로만 들어도 구조가 남는다 |
| 복선과 콜백 | 앞에서 예고 → 클라이맥스에서 회수 → 엔딩이 받는다 |
| 청중 호출로 끝내기 | "이번엔 여러분이 가져가실 차례" |

## 4. 표기

- **화면 대본(`text`)과 음성 대본(`tts`)을 처음부터 나눈다.** `text` 는 읽기 쉬운 원래 표기(ABC · 800 · AI), `tts` 는 숫자 · 영문을 한글로(에이비씨 · 팔백 · 에이아이 · 큐에이 · 시월 구일)
- **회사 · 브랜드 · 제품 이름을 어떻게 읽을지는 발표자에게 먼저 묻는다.** 영문과 숫자가 섞인 이름은 읽는 법이 여럿이다(한 자리씩 · 숫자로 · 영어로)
- 화자 시점: 발표자 본인이 말한다. 팀원 이름은 화면과 대본에서 빼거나 역할로(디자이너 1 · 2 · 3)
- "0건 · 모두 · 한 번도 · 전부" 같은 단정 문장은 원천 데이터(시트 · 티켓 · 저장소)로 다시 센다

## 5. 분량

- **짐작하지 말고 TTS 로 잰다.** 필재는 공백 포함 분당 약 460~480자(문단 사이 쉼 포함). 10분 ≈ 4,600~4,800자
- 사람이 직접 말하면 TTS 보다 길다. 실측: 필재 7분 24초짜리 대본이 사람 속도(0.85배)로 약 8분 40초
- Typecast 과금은 공백 포함 1자 = 1크레딧이고 무료 플랜 크레딧은 한정돼 있다. `tools/tts.py` 를 그냥 돌리면 계획(새로 만들 문단 · 크레딧 · 남은 크레딧)만 보여 준다. `--go` 는 크레딧을 쓰니 계획을 보여 주고 진행한다
- 대본도 처음부터 발표 폴더의 `deck/data.js` 에 쓴다. 장면이 없어도 `tts.py --go` 로 음성을 만들어 `deck/audio/NN.m4a` 를 통으로 들을 수 있다. 대본 파일과 음성 도구를 따로 두면 기기 · 세션이 바뀔 때 정본과 도구가 두 벌이 된다

### Typecast 키 넣기 (처음 한 번, 기기마다)

1. Typecast 에 로그인해 API 키를 발급받는다(https://studio.typecast.ai/developers/api)
2. 터미널에서 `security add-generic-password -U -a "$USER" -s typecast-api-key -w` 를 실행하고, 묻는 칸에 키를 붙여 넣는다
3. 키는 대화 · 파일 · 명령 인자 어디에도 남기지 않는다. `tts.py` 가 키체인에서 직접 읽는다

## 6. 피드백 받기: 공유 문서 표

통으로 들어 본 사용자가 "예시 · 맥락을 바꾸고 싶다"고 하면 파트별 표로 코멘트를 받는다(Confluence · Notion · Google Docs 등 코멘트를 달 수 있는 문서).

- 파트마다: 제목(+ 길이) → **발표 전략**(굵은 라벨 + 목록, 표 밖) → 파트 음성 → 표(`#` · 대본 · 코멘트)
- 표 첫 줄은 회색 `맥락` 행(파트 흐름 · 순서 지시), 그 아래 문단 행(문장 지시). 코멘트 칸은 비워 둔다
- 문서가 자동 저장되는 도구라면 **통째로 덮어쓰지 않는다.** 쓰기 직전 다시 읽고, 필요한 블록만 넣고, 쓴 뒤 코멘트 칸이 그대로인지 다시 센다
- 코멘트를 반영해 v2 를 data.js 에 넣고, **그때부터 정본은 data.js 다.** 프로젝트 노트 맨 위에 `정본: <발표 폴더>/deck/data.js` 한 줄

## 7. 다듬기

마지막 말맛은 발표자가 리허설하며 발표자 화면에서 고친다(엔진 문서 '대본 고치기'). 초안은 구조와 사실에 집중한다.
실제로 앞쪽 네 파트 20문단을 발표자가 직접 고쳤고, ▶ 는 대부분 "말을 다 한 뒤"로 옮겼다.
